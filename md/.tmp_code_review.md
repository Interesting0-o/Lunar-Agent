# Lunar 状态引擎深度代码审查报告

> 审查范围：`state_engine.py`、`state.py`、`default_state.py`、`nodes.py`、`perception.py`、`state_formatter.py`、`agent.py`  
> 审查视角：计算心理学 / AI 角色引擎 / 系统工程  
> 日期：2026-06-15

---

## 0. 执行摘要

Lunar 项目实现了一个**三层心理状态机**（内部状态、关系状态、表面状态）+ 一个**感知层**（LLM 提取 7 维心理刺激），整体架构方向正确，但当前实现仍停留在"概念验证"阶段。代码中大量硬编码权重、缺乏数学稳定性验证、缺失记忆/时间/目标/用户建模等关键子系统，且与心理学理论的对应关系较为粗糙。下面按 **致命 / 严重 / 中等 / 轻微** 四级分类列出全部问题。

---

## 1. 致命级问题（Critical）

### 1.1 LSTM 式门控更新的数学不稳定性

- **问题描述**：`update_internal_dynamics` 使用
  ```
  h_t = f ⊙ h_{t-1} + i ⊙ (A·h_{t-1} + B·e_t) + g ⊙ bias
  ```
  三个门 `f, i, g` 由三个独立的 sigmoid 生成，均 ∈ (0,1)。标准 LSTM 的关键设计是 **cell state** 与 **output** 分离，并通过 `i = 1 - f`（或耦合门控）保证状态不会无界增长/坍缩；而此处没有 cell state，三个门可以任意叠加（和 ∈ (0, 3)）。
- **影响**：
  - 若三门之和 < 1，状态会快速坍缩到接近 0；
  - 若三门之和 > 1，再加上 `bias` 与 `raw_dynamics` 均为正，状态会迅速饱和到 1；
  - 同一角色在不同输入下可能表现出完全相反的"情绪放大/清零"行为，不可解释。
- **代码位置**：`state_engine.py:438-444`
- **依据**：Hochreiter & Schmidhuber (1997) 的 LSTM 通过遗忘门与输入门耦合（Gers et al., 2000 进一步引入 peephole 与 coupled forget/input gates）来保证梯度与状态稳定性。独立三门无约束会破坏这一不变量。

### 1.2 "动态衰减"公式实为可发散的放大算子

- **问题描述**：`apply_decay` 实现为
  ```
  state[t] = baseline + (state[t-1] - baseline) × decay
  ```
  而 `compute_dynamic_decay` 将内部状态 decay clamp 到 `[0.70, 1.05]`，关系状态 clamp 到 `[0.95, 1.005]`。当 `decay > 1` 时，系统不是"衰减"而是**指数放大**偏离基线的量。
- **影响**：
  - 内部状态只要某轮因共振条件（如 `stimuli[ST_ABANDONMENT] > 0.3` + 高依恋焦虑）使 `decay > 1`，就会持续远离基线，最终永久饱和在 0 或 1；
  - 关系状态的上限 `1.005` 意味着每次 tick 都有约 0.5% 的正反馈放大，长期必然饱和；
  - 与真实情绪调节完全相反：心理学中的 homeostatic recovery 要求 |decay| < 1。
- **代码位置**：`state_engine.py:585-591`、`state_engine.py:579-580`
- **依据**：动力系统稳定要求特征根 / 衰减系数位于单位圆内（Strogatz, *Nonlinear Dynamics and Chaos*）。将 "decay" 定义为可 >1 的量是术语误用，实际变成不稳定正反馈。

### 1.3 关系状态 A_rel 矩阵存在正反馈环

- **问题描述**：`_build_rel_state_coupling` 中，`AFFECTION → TRUST → SAFETY → AFFECTION`、`AFFECTION → FAMILIARITY → SAFETY → AFFECTION` 等均为正耦合，对角线仅 0.90，总耦合强度可超过 1。
- **影响**：即使没有冲突刺激，关系状态也会因正反馈环自发增长并饱和到 1.0，导致"好感/信任/安全感"很快封顶，失去动态变化空间。
- **代码位置**：`state_engine.py:651-666`
- **依据**：LTI 系统稳定的充要条件是所有特征值模 < 1。该矩阵未做谱半径校验。

### 1.4 没有真正的时间模型

- **问题描述**：状态更新以"消息"为 tick，完全忽略 wall-clock 时间。`ENERGY`、`SOCIAL_BATTERY`、`MENTAL_FATIGUE` 的恢复/衰减与用户实际上一条消息间隔无关。
- **影响**：
  - 用户狂发 20 条消息与隔了 8 小时发 1 条消息产生相同的疲劳/恢复；
  - 无法模拟睡眠、休息、想念随时间累积等关键心理现象；
  - "等待"是角色核心设定，但引擎没有任何"等待时间"维度。
- **代码位置**：`state_engine.py` 全文件、`nodes.py:47-63`
- **依据**：时间心理学（Time Perspective Theory, Zimbardo & Boyd, 1999）与情绪动力学（Kuppens et al., 2010）均强调时间尺度对情绪恢复的决定性作用。

### 1.5 缺失记忆系统

- **问题描述**：系统仅保存 `messages` 与当前状态向量，没有 episodic memory、语义记忆、记忆巩固、遗忘曲线、记忆检索机制。`context_window = 4` 的感知上下文意味着模型只能看到最近 2 轮对话。
- **影响**：
  - 角色无法记起用户昨天说过的话、承诺、偏好；
  - 无法形成长期叙事自我（narrative self），与角色"等待了漫长岁月"的设定直接冲突；
  - 关系状态 `relationship_state` 成为唯一"长期记忆"，但它维度极低且数学不稳定。
- **代码位置**：`perception.py:25-29`、`config.py:10-19`、`state.py:221-240`
- **依据**：Conway & Pleydell-Pearce (2000) 的自我记忆系统（Self-Memory System）指出，长时记忆是人格一致性的根基。没有记忆的角色不可能稳定人格。

### 1.6 没有目标/动机/行动倾向系统

- **问题描述**：引擎只有"刺激 → 状态变化 → 表面表达"，没有角色的目标、意图、需求层级、行动倾向（action tendency）。
- **影响**：
  - 角色只是被动反应，不会主动追求亲密、寻求安慰、回避冲突或策划行为；
  - LLM 生成的行为缺乏自上而下的动机约束，容易 drift；
  - 无法解释真实情绪的功能性（Frijda, 1986）。
- **代码位置**：`state_engine.py` 全文件、`character_prompt.py`
- **依据**：Appraisal Theory（Scherer, 2005）、OCC 模型（Ortony et al., 1988）均将目标一致性作为情绪产生的核心条件。

## 2. 严重级问题（High）

### 2.1 状态维度不足以表达复杂人格

- **问题描述**：
  - InternalState 仅 8 维：energy, stress, loneliness, insecurity, irritation, longing, social_battery, mental_fatigue；
  - 缺少 valence/arousal（Russell 情感环）、基本情绪（joy, sadness, fear, anger, disgust, surprise）、认知评价（appraisal）维度、自尊状态、悲伤、羞耻、内疚、兴奋等；
  - 所有情绪都被归约为"压力/孤独/不安"三个轴，表达能力严重不足。
- **影响**：角色心理画像扁平化，无法区分"悲伤但平静"、"愤怒但压抑"、"嫉妒但装作无所谓"等 nuanced 状态。
- **代码位置**：`state.py:98-117`
- **依据**：Russell (1980) 的 circumplex model 至少需要 valence × arousal 两个连续维度；Ekman 的基本情绪理论至少需要 6 种情绪类型。

### 2.2 特质维度与心理学五大人格/依恋理论对应粗糙

- **问题描述**：Traits 包含 sensitivity, pride, emotional_openness, emotional_stability, optimism, anxiety_proneness, anger_reactivity, jealousy_sensitivity, attachment_anxiety, attachment_avoidance。虽然有依恋维度，但：
  - 缺少 Big Five 的 conscientiousness、extraversion、agreeableness；
  - "pride" 用 0~1 标量描述人格极不常见，更接近状态；
  - 多个维度高度相关（emotional_stability 与 anxiety_proneness 近乎反相），存在多重共线性；
  - 特质被声明为"长期稳定"，但代码中没有任何特质演化机制。
- **影响**：角色卡难以与主流人格模型互通；不同维度间会互相抵消或重复放大，调参困难。
- **代码位置**：`state.py:78-96`、`default_state.py:21-34`
- **依据**：McCrae & Costa (1992) 五因素模型；Bartholomew & Horowitz (1991) 成人依恋四类型模型。

### 2.3 没有用户模型 / Theory of Mind

- **问题描述**：系统只维护一个 `relationship_state`（对用户的关系感知），没有关于用户人格、偏好、情绪、目标、信念的独立模型。感知层把"用户输入"直接映射为对角色自己的刺激，而没有"用户现在是什么状态 / 意图"的推断。
- **影响**：
  - 角色无法区分"用户真的生气"与"用户在开玩笑"；
  - 无法形成互惠性预期（reciprocity）与信任推理；
  - 亲密关系的双向建模缺失。
- **代码位置**：`perception.py`、`state_engine.py`
- **依据**：Theory of Mind（Premack & Woodruff, 1978）是社交互动的核心；依恋理论中"内部工作模型"包含对自我和他人的双向表征（Bowlby, 1969/1982）。

### 2.4 感知层严重依赖弱本地模型且输出 schema 脆弱

- **问题描述**：`perception_model` 使用本地 `qwen2.5:7b`（Ollama），提示词要求输出严格 JSON。重试机制只有 3 次，失败则整轮结束。
- **影响**：
  - 7B 模型对微妙语气、反话、多轮上下文的心理学解读能力有限；
  - 任何 JSON 解析失败都导致本轮无回复；
  - 没有 fallback、没有置信度、没有多模态感知。
- **代码位置**：`model.py:15-20`、`perception.py:49-99`、`config.py:10-19`
- **依据**：LLM-as-a-judge / structured extraction 研究表明，较小模型在细粒度情感标注任务上错误率显著高于较大模型或专用分类器（Zheng et al., 2023）。

### 2.5 表面状态不持久化

- **问题描述**：`SurfaceState` 被设计为"动态投影，不存储"（`state.py:188`）。
- **影响**：
  - 无法分析角色表达风格的长期变化；
  - 无法将上一轮的 surface 作为本轮输入（情绪惯性/表达惯性）；
  - LLM 无法感知"我上一秒还很尖锐，现在要收敛"的连续性。
- **代码位置**：`state.py:52-65`、`state_engine.py:604-641`
- **依据**：情绪表达具有时间连续性（Kuppens et al., 2010），表面行为也应是状态变量的一部分。

### 2.6 缺少状态不确定性 / 概率建模

- **问题描述**：所有状态都是点估计（point estimate），没有方差/置信度。感知输出、门控、衰减都是确定性值。
- **影响**：
  - 无法表达"我不确定用户是不是在讽刺"这种关键心理；
  - 无法做贝叶斯更新；
  - 对噪声输入过度敏感。
- **代码位置**：全文件
- **依据**：概率图模型 / 卡尔曼滤波是感知-状态估计的标准做法（Kalman, 1960）。

### 2.7 衰减基线固定，忽略人格基线

- **问题描述**：`apply_decay` 始终向 `DEFAULT_INTERNAL` / `DEFAULT_RELATIONSHIP` 回归，而不是向角色自身的 trait-determined setpoint 回归。
- **影响**：
  - 一个高焦虑角色按理说应有更高的 baseline stress，但系统会把它拉回到 0.2；
  - 无法刻画"慢性焦虑"、"慢性孤独"等人格-状态耦合现象。
- **代码位置**：`state_engine.py:585-591`、`default_state.py:36-47`
- **依据**：情感动力学中的"trait-state congruence"（Kuppens & Van Mechelen, 2007）指出情绪基线应由人格决定。

### 2.8 硬编码阈值造成不连续行为

- **问题描述**：`compute_dynamic_decay` 中大量使用硬编码阈值：
  ```python
  if stimuli[ST_ABANDONMENT] > 0.3 and traits[T_ATTACHMENT_ANXIETY] > 0.55:
      ...
  ```
  这类 if-else 在阈值处产生阶跃。
- **影响**：
  - 0.299 与 0.301 的刺激强度导致截然不同的系统行为；
  - 与心理学中"连续变化"的直觉冲突；
  - 难以用梯度方法调参或学习。
- **代码位置**：`state_engine.py:557-576`
- **依据**：连续动态系统应避免非平滑切换；Sigmoid 等软阈值已在门控中使用，但衰减层回退到硬阈值。

### 2.9 缺少 LLM 生成状态的反馈校验

- **问题描述**：`state_description` 被注入 LLM 后直接生成回复，但没有任何机制验证 LLM 的回复是否真实符合了指定的 surface/internal/relationship 状态。
- **影响**：
  - LLM 可能忽略状态描述，生成与角色状态不符的回复；
  - 没有训练/评估闭环，无法迭代改进；
  - 角色一致性仅靠 prompt engineering，不可靠。
- **代码位置**：`nodes.py:106-117`、`state_formatter.py`
- **依据**：强化学习 from Human Feedback (RLHF) / 角色一致性评估（Shanahan et al., 2023）强调需要输出-状态对齐的监督信号。

## 3. 中等级问题（Medium）

### 3.1 G_LEAKAGE 门控被定义但从未使用

- **问题描述**：`GateVector` 声明了 4 维，但 `G_LEAKAGE` 只在注释中提到"保留索引，不再使用"。
- **影响**：增加状态维度与认知负担，却无功能；`G_SIZE = 4` 导致数组中有一个无意义维度。
- **代码位置**：`state.py:169-180`、`state_engine.py:136-137`
- **依据**：YAGNI 原则；维度诅咒。

### 3.2 刺激调制系数可能过度放大

- **问题描述**：`_compute_stimulus_modulation` 中
  ```python
  return (1.0 + trait_amp) * (1.0 + rel_amp)
  ```
  当 trait_amp 与 rel_amp 同向时，调制系数可达 2.0 以上，再乘以原始刺激后仍无上限，直到 `soft_clamp` 才截断。
- **影响**：高敏感/高焦虑角色在特定关系中会出现极端放大，失去可解释性。
- **代码位置**：`state_engine.py:202-233`
- **依据**：乘法放大器应增加上限约束或改用对数/softmax 组合。

### 3.3 `_sigmoid_gate` 的阈值被外部缩放破坏

- **问题描述**：`_sigmoid_gate(x) = sigmoid(x - 0.5)`，意图在 0.5 处软阈值。但实际输入如 `trait_supp * rel_supp + internal_supp` 中，`rel_supp` 可能达到 1.35，导致输入中心偏离 0.5，软阈值位置漂移。
- **影响**：门控响应区间与心理学预期不一致。
- **代码位置**：`state_engine.py:120-125`、`state_engine.py:162`
- **依据**：门控设计应保证输入经归一化后再通过固定阈值激活函数。

### 3.4 压抑门语义前后不一致

- **问题描述**：
  - `apply_gates` 中 `suppression` 用于衰减 `outer_stimuli`（外表情），注释说"高压抑：outer 远弱于 inner"；
  - `update_internal_dynamics` 的 `i_gate` 却用 `gates[G_SUPPRESSION]` 来降低内部接受度。
- **影响**：同一概念在门控层与动力学层承担不同甚至矛盾的角色，设计者/调试者容易混淆。
- **代码位置**：`state_engine.py:252-269`、`state_engine.py:411-419`
- **依据**：概念一致性是复杂系统可维护性的关键。

### 3.5 关系动力学缺少门控与个性化

- **问题描述**：`update_relationship_dynamics` 完全 LTI，没有特质调制、没有情境门控、没有防御性贬低（devaluation）等依恋相关机制。
- **影响**：关系演变过于线性，无法表达"焦虑型依恋者在被冷落后突然降低信任"等非线性模式。
- **代码位置**：`state_engine.py:706-714`
- **依据**：依恋理论中的"内部工作模型"会在威胁情境下激活防御性策略（Mikulincer & Shaver, 2007）。

### 3.6 序列化兼容性靠打补丁

- **问题描述**：`state.py` 用 `_PydanticArray`  hack 让 Pydantic 把 ndarray 当成 list；`nodes.py` 和 `state_formatter.py` 中多处手动 `isinstance(v, list)` 转回 ndarray。
- **影响**：
  - 任何新增节点都容易忘记转换；
  - LangGraph checkpoint 序列化/反序列化行为不可控；
  - 类型标注与实际运行时类型不一致。
- **代码位置**：`state.py:30-49`、`nodes.py:26-33`、`state_formatter.py:261-281`
- **依据**：应使用 Pydantic 自定义序列化器或明确将状态表示为可序列化结构（如 dataclass + converter），而非运行时类型 hack。

### 3.7 test.json 使用过期 schema

- **问题描述**：`test.json` 仍包含 `user_signals`、`user_interaction_impact` 等已在 `state.py` 中移除的字段。
- **影响**：加载该文件会导致 State 中残留无用字段，误导调试。
- **代码位置**：`test.json`
- **依据**：配置文件应与代码 schema 同步。

### 3.8 没有单元测试 / 不变量验证

- **问题描述**：项目中没有任何 `*_test.py` 或 `test_*.py` 文件。
- **影响**：
  - 无法验证数学稳定性、门控范围、状态边界；
  - 重构风险极高；
  - 无法做回归测试。
- **代码位置**：项目根目录
- **依据**：任何动力系统引擎都应至少包含不变量测试（state ∈ [0,1]、能量守恒/有界、长时间模拟不发散）。

### 3.9 `extract_recent_context` 回退逻辑可能包含 SystemMessage

- **问题描述**：当没有 Human/AI 消息时，回退到 `messages[-1:]`，可能拿到 SystemMessage。
- **影响**：感知模型可能把系统提示词本身当作用户输入分析。
- **代码位置**：`perception.py:25-29`
- **依据**：感知上下文应明确排除系统消息。

### 3.10 感知验证只检查类型，不检查数值范围

- **问题描述**：`validate_perception_result` 只验证字段存在且为 int/float，不验证 ∈ [0,1]。
- **影响**：LLM 可能输出越界值（如 1.2 或负数），直接污染动力系统。
- **代码位置**：`perception.py:32-46`
- **依据**：所有来自外部模型的标量输出都应做值域校验。

### 3.11 `_ensure_array` 返回 `None` 并标注 `#type:ignore`

- **问题描述**：`_ensure_array` 在输入为 None 时返回 None，但返回类型注解为 `np.ndarray`。
- **影响**：类型系统失效，运行时可能在后续代码中触发 `TypeError`。
- **代码位置**：`nodes.py:26-33`
- **依据**：应使用 `Optional[np.ndarray]` 返回类型或明确抛出异常。

### 3.12 人格偏置向量 `_build_personality_bias` 过度简化

- **问题描述**：偏置向量只有 3 个非零元素（energy +0.01, loneliness -0.005, irritation -0.01），其他维度靠 per-tick 临时加减，且数值极小。
- **影响**：无法形成鲜明的性格驱动力；所有角色都会以相似速率向默认基线回归。
- **代码位置**：`state_engine.py:357-363`
- **依据**：人格应通过 setpoint、时间常数、刺激权重共同体现（see Cybernetic Big Five Theory, DeYoung, 2015）。

### 3.13 表面投影缺少内部-外部交互项

- **问题描述**：`project_surface` 先算内部基线，再把 `outer_stimuli` 作为独立加性项。没有考虑"内部高压力 + 外部高冲突"的协同放大，也没有"内部高能量 + 外部认可"的乘性增强。
- **影响**：表面状态对复合情境的区分能力不足。
- **代码位置**：`state_engine.py:604-641`
- **依据**：情绪表达是内部状态与情境交互的结果（Scherer 的 Component Process Model）。

## 4. 轻微级问题（Low）

### 4.1 魔法数字遍布全文件

- **问题描述**：所有矩阵权重、门控系数、衰减偏置都是硬编码的 0.05、0.08、0.12 等魔法数字，没有配置文件、命名常量或学习机制。
- **影响**：调参困难，可解释性差，难以针对不同角色复用。
- **代码位置**：`state_engine.py` 全文件
- **建议**：将权重提取为 `trait_influence_config` / `coupling_config`，或提供 YAML/JSON 配置。

### 4.2 `_sigmoid` 总是返回 float64

- **问题描述**：`np.empty_like(x, dtype=np.float64)` 会忽略输入 dtype，强制 double。
- **影响**：微小性能与内存开销；类型不一致。
- **代码位置**：`state_engine.py:110-117`
- **建议**：`np.empty_like(x)` 即可。

### 4.3 `tui_test` 首条消息处理逻辑复杂且脆弱

- **问题描述**：`agent.py:108-114` 用 `is_inject_system` 标志控制是否加载 `test.json`，并通过 `pop("has_inject_system_prompt")` 触发系统提示注入。
- **影响**：
  - 测试入口与业务逻辑耦合；
  - 如果 `test.json` 已含 `has_inject_system_prompt: true`，首条消息不会注入 system prompt；
  - 没有错误处理。
- **代码位置**：`agent.py:71-127`

### 4.4 `main.py` 几乎是空实现

- **问题描述**：`main.py` 只有一个 "Hello World" FastAPI 端点，与核心项目无关。
- **影响**：项目对外 API 缺失，无法作为服务运行。
- **代码位置**：`main.py`

### 4.5 日志级别与异常信息不足

- **问题描述**：当 perception 失败时，只记录 `logger.error`，没有向调用方返回任何错误信息或 fallback 状态。
- **影响**：TUI/服务层无法给用户任何反馈。
- **代码位置**：`perception.py:96-99`、`nodes.py:57-58`

### 4.6 感知提示词角色绑定过死

- **问题描述**：`PERCEPTION_SYSTEM_PROMPT` 硬编码了"月下誓约"角色背景。
- **影响**：如果想换角色，必须重写感知提示词；没有通用感知层。
- **代码位置**：`perception_prompt.py`
- **建议**：将角色背景从提示词模板参数化。

### 4.7 `state_formatter` 的 `_desc` 五档划分全局固定

- **问题描述**：所有维度使用相同的 0.15/0.35/0.55/0.75 阈值映射到五级文本。
- **影响**：某些维度（如 irritation）在 0.1 时已经"有些烦躁"，而某些维度（如 affection）0.1 仍是"冷淡"，用同一阈值不合理。
- **代码位置**：`state_formatter.py:30-52`

## 6. 修复优先级建议

1. **立即修复**：将 decay 严格限制到 <1（内部 <0.99，关系 <0.999），并引入 trait-dependent baseline；或改用 homeostatic recovery 公式。
2. **立即修复**：为 LSTM 式更新引入 cell state 或耦合门控，确保 `f + i + g ≈ 1` 或有界。
3. **高优先级**：验证 A、A_rel 矩阵的谱半径，确保 LTI 子系统稳定。
4. **高优先级**：引入 wall-clock 时间模型，将 tick 替换为 `dt`。
5. **高优先级**：增加记忆模块（至少短期情景记忆 + 长期摘要记忆）。
6. **高优先级**：建立单元测试，覆盖长时间模拟不发散、状态边界、门控范围等不变量。
7. **中优先级**：将硬编码权重提取为配置，支持多角色。
8. **中优先级**：为感知输出增加值域校验与置信度/不确定性。
9. **中优先级**：引入目标/动机系统，让角色具备主动行为。
10. **低优先级**：完善 `main.py` 服务化、错误反馈、日志。

---

## 7. 结论

Lunar 状态引擎在概念层面具备"连续人格动力系统"的雏形，门控-里外表情的分离、LTI 关系动力学等设计有心理学直觉支撑。但当前实现存在**致命级数学稳定性问题**（无约束三门 LSTM、decay 可 >1、关系矩阵正反馈），且缺失**记忆、时间、目标、用户建模**等角色引擎的核心子系统。大量硬编码权重、无测试、序列化 hack、无 LLM 输出校验等问题使其难以从 demo 走向生产。建议先修复数学基础与稳定性，再逐步补齐记忆与动机系统，最后建立评估与配置体系。
